# Regenerate the test report

`docs/test-report.md` is generated by `scripts/test_report.py` – never edit it by hand.

1. **Commit first.** The report records the git commit; with a dirty tree it says "+ uncommitted changes".
   Commit the code change, then commit the regenerated report separately ("Regenerate test report for <hash>").
2. **Databases:** `docker compose up -d db oracle` and wait until both are `healthy` (`docker compose ps`;
   Oracle needs 1–2 min on first start). External databases work as well: set `PG` / `ORA` in step 3 to their URLs.
   The report records version and row count of whatever it ran against.
3. **Environment:**
   ```bash
   export PG=postgresql+asyncpg://app:secret@localhost:5432/app_db
   export ORA='oracle+oracledb_async://app:secret@localhost:1521/?service_name=FREEPDB1'
   DATABASE_URL=$PG alembic upgrade head && DATABASE_URL=$ORA alembic upgrade head
   ```
4. **Data (only if the table is empty or the data generator changed):** the report states the row count.
   ```bash
   DATABASE_URL=${PG/+asyncpg/} python scripts/seed.py --count 50000 --truncate
   DATABASE_URL=${ORA/_async/} python scripts/seed.py --count 50000 --truncate
   ```
   The devcontainer VM disk is small (20 GB) – don't seed more than 50,000 rows per database without checking `df -h`.
5. **Start one API per backend** in the background and keep the pids (don't `pkill -f` – the pattern can match your own shell):
   ```bash
   DATABASE_URL=$PG  nohup uvicorn openapi_server.main:app --port 8001 > <scratchpad>/pg.log 2>&1 & echo $! > <scratchpad>/pg.pid
   DATABASE_URL=$ORA nohup uvicorn openapi_server.main:app --port 8002 > <scratchpad>/ora.log 2>&1 & echo $! > <scratchpad>/ora.pid
   ```
   Wait until `curl -sf 'http://127.0.0.1:800{1,2}/service?limit=1'` succeeds.
6. **Generate** (takes a few minutes, use a long timeout):
   ```bash
   python scripts/test_report.py --target "PostgreSQL|http://127.0.0.1:8001|$PG" --target "Oracle|http://127.0.0.1:8002|$ORA"
   ```
   `--bench-runs 0` skips the benchmark.
7. **Stop the APIs** via the pid files; leave the database containers running.
8. **Check:** the *Result* table (all passed on both backends), and that the plans for selective queries still show index
   access (PG: `Bitmap Index Scan` on the GIN index, Oracle: `INDEX RANGE SCAN (MULTI VALUE)`). If the latencies changed
   noticeably, update the performance table in `README.md`.
